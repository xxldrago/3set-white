<objective>
Close CR-01: bot-redirect login is exploitable as login-CSRF/account takeover because the claim cookie binds the consumer to the issuer but nothing binds the Telegram user who presses Start to the issuing browser. Add a device-code confirmation: the bot that receives `/start login_<token>` generates a short code, stores only its hash, and replies the code to the authorizing Telegram chat; the issuing browser must submit that code to consume. The attacker's browser cannot obtain the code from any API, and the victim sees a code they did not initiate.

Purpose: make anonymous bot-redirect login resistant to reverse fixation while keeping it usable.
Output: schema migration, service contract, bot reply, consume route, client code-entry state, integration tests including the hijack path.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> BFF | Token + claim cookie + confirmation code cross here; consume requires all three |
| telegram -> bot -> user | Bot delivers the confirmation code to the authorizing Telegram chat only |
| BFF -> DB | Only the code hash is persisted; the plaintext code is never stored or returned over HTTP |
