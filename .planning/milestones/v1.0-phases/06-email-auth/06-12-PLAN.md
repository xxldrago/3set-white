  <action>
Refactor `linkAccounts` so the merge decision is made INSIDE `prisma.$transaction`: re-read the loser row by `telegramId` within the transaction and re-assert `loser.id !== survivor.id`, `loser.email === null`, and `survivor.telegramId === null` (or already equal to `tg`); if an invariant fails, throw `AccountConflictError` (no merge). Keep the existing re-pointing (`KeyCache` dedupe + updateMany, `Order`, `Ticket`, `PasswordReset`, `Notification`), delete-before-inherit ordering, and `trialUsed OR` / first-non-null semantics. Wrap the transaction so Prisma `P2002`/`P2025`/`P2003` during the merge map to a typed outcome: `P2025` (loser/winner vanished) -> `AccountNotFoundError`; `P2002` (identity already attached) -> `AccountConflictError`. Never let these escape as an uncaught 500 for the caller. The no-loser fast path (attach the identity directly) stays, but the `user.update` P2002 race fallback must re-enter the transactional merge path rather than merging with a pre-read row.

Create `tests/integration/link-merge.test.ts` (real `setwhite` DB, throwaway telegram ids/emails): (1) pure-TG loser + email survivor merges, rows re-point, `trialUsed` OR, survivor gets the telegramId, loser deleted; (2) a telegramId already on an email-bearing account throws `AccountConflictError` and merges nothing; (3) linking an identity already on the survivor is idempotent (`merged:false`); (4) a synthetic `P2025` (spy on `tx.user.delete` or delete the loser mid-flight) surfaces as `AccountNotFoundError`, not a raw throw. Clean up rows in afterAll.
