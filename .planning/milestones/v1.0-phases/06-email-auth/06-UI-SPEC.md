# Phase 6 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Extends Phase 5's approved contract, which extends Phases 2–4.** Phases 2–5
already locked the spacing scale, the four type sizes / two weights, the 60/30/10 zinc + `#171717`
accent + `#dc2626` destructive palette, the semantic status-chip palette, the inline
destructive-confirm pattern (`ConfirmPanel`), the skeleton/error copy catalog, the input/button
recipes (`CreateTicketForm`, `UserSearchForm`), and the RU i18n discipline. Phase 6 **introduces no
new tokens, fonts, icons, or component library** — it composes the **email-auth surfaces**
(`/login` rework, registration, password reset, «Аккаунт» section) from the same primitives and adds
one new form-field state mapping (field-level validation errors) plus one new confirm variant usage
(unlink login method) that reuse existing hex.

**Scope boundary.** AUTH-01..AUTH-06 only. Trial/badge/key/payment/ticket/admin surfaces are
**unchanged** — email users see the same cabinet (per CONTEXT). Bot stays TG-only (D-94): no
email UI in the bot. SMTP delivery, hashing, backoff, and merge logic are server-side and have no
visual surface beyond the copy contracted here.

**shadcn gate:** `components.json` absent; stack is Next.js 16 + React 19. The gate was resolved
**No** upstream (Phase 2 Design System; Phases 1/3/4/5 re-confirmed; the phase brief mandates
hand-rolled Tailwind with no component library). `npx shadcn info` is therefore not runnable —
**Tool: none**. No preset initialized this phase. Registry safety gate: not applicable.

**Auth-specific rendering & access dependencies (contract, not decoration):**
- **Session is the same httpOnly cookie (jose) for email and Telegram login** (D-86). Email-auth
  client islands never read, write, or render any session value — they POST credentials to BFF routes
  and follow redirects, exactly like `LoginButton`'s `postPayload` discipline.
- **Bot is TG-only** (D-94). No email form, reset link, or account-linking UI appears in the bot.
  The «Аккаунт» section and all reset surfaces are cabinet-only.
- **Rate-limit/backoff (D-84) is surfaced, never silent.** A 429 from any auth route renders
  `auth.rateLimited` («Слишком много попыток. Повторите через {n} сек.») with the server-provided
  wait; the submit stays locked until the wait elapses. No countdown fabrication client-side — the
  number comes from the server response.
- **No user enumeration on login** — wrong email and wrong password render the identical generic
  copy. The sole exception is the reset-request form, where the honest «no account» answer is
  **explicitly accepted by the owner** (D-89) and therefore contracted as its own keyed copy.

## Auth Surfaces & Interaction Contract

### 1. `/login` rework — email form on top, Telegram below, centered flow (AUTH-06)

Layout (D-91 — this layout **is** the AUTH-06 fix):

- Page keeps the standard shell (`bg-zinc-50 font-sans dark:bg-black`, `main px-6 py-12 sm:px-16`).
  Inside, a single centered column `mx-auto flex w-full max-w-md flex-col gap-6` holds **both**
  auth methods in normal document flow.
- **Order top → bottom:** (1) `EmailAuthCard`, (2) a divider row (`auth.orContinue`,
  «или» — 14/400 secondary ink with hairline rules on both sides), (3) `TelegramWidgetSlot`
  containing the existing `LoginButton`, (4) `InstallPrompt` (unchanged, existing position).
- **The AUTH-06 defect** (widget iframe injected by `telegram-widget.js` escaping layout and
  landing bottom-left on desktop) is fixed by containment, never by absolute positioning:
  - `TelegramWidgetSlot` is `flex min-h-24 flex-col items-center justify-center gap-3` —
    `items-center` forces the injected iframe (an inline replaced element appended by the
    third-party script) to center; `min-h-24` reserves space so there is no layout shift when the
    script injects late.
  - No `absolute` / `fixed` / float / negative-margin positioning is permitted on the slot, the
    iframe, or `LoginButton`. The widget and the email form are siblings in the same flex column.
  - The slot renders `login.widgetNote` beneath the widget (existing copy, kept).
- Heading block unchanged in hierarchy: `h1` 30/600 `login.title`, sub 16/400 `login.text`.
  Heading copy is updated (see Copywriting Contract) to name both methods.

`EmailAuthCard` anatomy (card surface, `flex flex-col gap-5`):

- **Mode switch** — segmented control with two segments: `auth.modeLogin` («Вход») /
  `auth.modeRegister` («Регистрация»). Selected segment uses the accent fill
  (`bg-foreground text-background`); unselected uses the secondary recipe. Deep-linkable via
  `?mode=register`; default mode is `login`. Switching mode clears field errors and the generic
  failure, retains the typed email, and clears both password fields.
- **Email field:** `<label>` with `FIELD_LABEL` (`auth.emailLabel`, «Email»), `<input
  type="email" autoComplete="email" required>` with the INPUT recipe, placeholder
  `auth.emailPlaceholder` («you@example.com»). Value is trimmed on submit; client checks only
  non-blank + `[^@\s]+@[^@\s]+\.[^@\s]+` shape — anything deeper is server-validated.
- **Password field** (`PasswordField`): label `auth.passwordLabel` («Пароль»), input
  `type="password"` / `autoComplete="current-password"` (login) or `"new-password"` (register),
  `minLength=8`. Show/hide toggle is a secondary-style 44×44px button (`auth.showPassword` /
  `auth.hidePassword`, «Показать» / «Скрыть») that flips `type` and never clears the value.
- **Register mode adds nothing except policy hint:** `auth.passwordHint` («Минимум 8 символов.»,
  14/400 secondary) under the password field (D-85: min 8, no complexity rules).
- **Submit:** primary `w-full` — `auth.loginCta` («Войти») / `auth.registerCta`
  («Создать аккаунт»). Disabled while email blank, password blank, or a request is in flight.
  In-flight → label swaps to `auth.loginCtaLoading` («Входим…») / `auth.registerCtaLoading`
  («Создаём аккаунт…») and the button + both fields lock (double-tap cannot create two accounts).
- **Reset link (login mode only):** text link `auth.forgotPassword` («Забыли пароль?») under the
  submit → `/reset`. Body-link style (underline, secondary ink) — accent is not used for body links.
- **Field errors** render per-field under the field, `role="alert"`, 14/400
  `text-red-600 dark:text-red-400`, invalid field gets `border-red-600/50 dark:border-red-400/50`
  (ring only — no layout shift, the slot is always reserved):
  - `auth.emailInvalid` («Введите корректный email.») — malformed email.
  - `auth.passwordTooShort` («Пароль — минимум 8 символов.») — register / reset-confirm / change.
  - `auth.passwordsMismatch` («Пароли не совпадают.») — reset-confirm repeat.
  - `auth.fieldRequired` («Заполните это поле.») — blank submit via Enter.
- **Generic failure (no enumeration):** wrong email and wrong password render the identical
  `auth.invalidCredentials` («Неверный email или пароль. Проверьте данные и попробуйте ещё раз.»)
  in a `role="alert"` block with a `common.retry`-less static state (the form stays filled except
  passwords clear). Never distinguish «нет такого пользователя» from «неверный пароль» here.
- **Rate limit:** 429 → `auth.rateLimited` («Слишком много попыток. Повторите через {n} сек.»),
  submit locked until the server-provided wait elapses; `{n}` via `t()` interpolation.
- **Success:** login → `window.location.href = '/'` (same as `LoginButton.postPayload`).
  Register (AUTH-01: no verification, instant login) → same redirect; welcome email (D-90) is
  server-side, with no UI surface beyond the redirect.

### 2. Password reset — request (`/reset`) + confirm (`/reset/confirm`)

Both pages reuse the shell + `max-w-md` centered column + card surface. No auth gate (signed-out
only surfaces; a signed-in visitor is redirected to `/`).

`ResetRequestForm` (card, `flex flex-col gap-5`):

- Heading `auth.resetTitle` («Сброс пароля») as `h1` 30/600 + intro `auth.resetIntro`
  («Введите email — пришлём ссылку для сброса. Ссылка действует 1 час.»).
- One email field (same recipe/label/placeholder as §1) + primary submit `auth.resetRequestCta`
  («Отправить ссылку»), disabled while blank or in flight; in-flight → `auth.resetRequestLoading`
  («Отправляем…»).
- **Sent (existing email):** success panel `auth.resetSent` («Ссылка отправлена. Проверьте почту —
  ссылка действует 1 час.») in a `role="status"` region; the form collapses to a
  `common.retry`-free static state with a «Вернуться ко входу» link (`auth.backToLogin`).
- **Honest no-account answer (D-89, owner-accepted):** `auth.resetNoAccount`
  («Аккаунт с таким email не найден. Проверьте адрес или создайте аккаунт.») with a link to
  `/login?mode=register`. This is the **only** surface where account existence is disclosed.
- **Error:** `auth.resetError` («Не удалось отправить письмо. Попробуйте ещё раз.») + `common.retry`;
  typed email retained. No SMTP/provider detail rendered.

`ResetConfirmForm` (card, `flex flex-col gap-5`; token read server-side from the URL):

- Heading `auth.resetConfirmTitle` («Новый пароль»).
- Two `PasswordField`s: `auth.newPasswordLabel` («Новый пароль», `autoComplete="new-password"`) +
  `auth.repeatPasswordLabel` («Повторите пароль», `autoComplete="new-password"`). Policy hint
  `auth.passwordHint` under the first. Submit primary `auth.resetConfirmCta`
  («Сохранить пароль»), disabled while either blank or in flight; in-flight →
  `auth.resetConfirmLoading` («Сохраняем…»).
- **Success:** `auth.resetDone` («Пароль обновлён. Войдите с новым паролем.») + primary link
  `auth.backToLogin` («Вернуться ко входу») → `/login`. Session from the reset is **not**
  auto-established — the user logs in explicitly.
- **One-time 1-hour token states (D-88)** — each its own keyed panel, `role="alert"`, typed
  passwords cleared, no token value rendered:
  - invalid/malformed → `auth.resetInvalid` («Ссылка недействительна. Запросите новую.»)
  - expired (>1h) → `auth.resetExpired` («Ссылка истекла — ей больше часа. Запросите новую.»)
  - already used → `auth.resetUsed` («Эта ссылка уже использована. Запросите новую.»)
  - each panel carries a secondary «Запросить новую ссылку» action → `/reset`.
- **Error:** `auth.resetError` + `common.retry`; typed passwords cleared.

### 3. «Аккаунт» section — link/unlink Telegram, change password (D-92)

Location: cabinet home (or settings route if the executor introduces one — the contract binds the
**cards**, not the route). Server-rendered; loading → `SkeletonRows`; error → `common.errorLoad` +
`common.retry` for the section only (trial/keys/payments render independently).

- **Section heading** `auth.accountTitle` («Аккаунт») 20/600. Intro `auth.accountIntro`
  («Способы входа и пароль.») 14/400 secondary.
- **Login-methods list** — one row per method, card surface, row anatomy: method label + status
  line + action:
  - Email row: `auth.methodEmail` («Email») + the address (`tabular-nums`, truncated 1 line with
    `title`). Email cannot be changed or removed in Phase 6 (no copy for it — absence is the contract).
  - Telegram row linked: `auth.methodTelegram` («Telegram») + `auth.tgLinked` («Привязан: {id}») +
    secondary `auth.unlinkCta` («Отвязать»).
  - Telegram row unlinked: `auth.tgNotLinked` («Не привязан») + primary-compact
    `auth.linkCta` («Привязать Telegram») which opens the same widget in a bounded
    `TelegramWidgetSlot` inline (the slot rules from §1 apply — centered, in-flow).
- **Link entry points:** the «Аккаунт» row above is the primary one; a secondary entry —
  `auth.linkBanner` («Привяжите Telegram, чтобы входить в один тап и получать уведомления.»)
  rendered as a dismissible-free info card on the cabinet home **only** for email users without a
  linked Telegram — links scroll to / open the «Аккаунт» section. No badge/trial/key surface is
  touched by linking (same cabinet guarantee).
- **Unlink confirm** (`UnlinkConfirmPanel`, destructive red — unlinking removes access):
  first tap opens the inline panel; copy `auth.unlinkTitle` («Отвязать Telegram?») /
  `auth.unlinkBody` («Вы потеряете вход через Telegram. Email-вход сохранится.») /
  confirm `auth.unlinkConfirm` («Отвязать»). **Last-method case (D-93, owner-accepted lockout
  risk):** body swaps to `auth.unlinkLastBody` («Это последний способ входа. Вы можете потерять
  доступ — восстановление только через поддержку.») and confirm to `auth.unlinkLastConfirm`
  («Всё равно отвязать»). Escape / `common.cancel` → no request; mutation only on the explicit
  second tap; never `window.confirm`. Failure → `auth.unlinkError` + `common.retry`.
- **`ChangePasswordForm`** (card, `flex flex-col gap-5`): heading `auth.changePasswordTitle`
  («Смена пароля») 20/600; `PasswordField` current (`auth.currentPasswordLabel`, «Текущий пароль»,
  `autoComplete="current-password"`) + `PasswordField` new (`auth.newPasswordLabel` + hint) +
  primary `auth.changePasswordCta` («Обновить пароль»), same lock/loading discipline
  (`auth.changePasswordLoading`, «Обновляем…»). Success → `auth.passwordChanged`
  («Пароль обновлён.») in `role="status"`; fields clear. Wrong current password renders the
  generic `auth.invalidCredentials`--analog `auth.currentPasswordWrong` («Неверный текущий пароль.»)
  — current-password check is not an enumeration surface. Logout stays common (`common.logout`
  equivalent, existing session route — D-86 shared logout).

### 4. What Phase 6 does NOT change

- Trial button/flow, tariff picker, «Мои подписки», key detail (sub-link/QR/traffic/guides),
  device management, payment surfaces, ticket surfaces, admin panel: **zero visual change**.
  Email users see byte-identical cabinet surfaces once signed in.
- `InstallPrompt`, guides, support entry: unchanged.
- No new status chips, no new badge, no «email verified» indicator (no verification in Phase 6 —
  inventing one is forbidden).

## Spacing Scale

Reuses the Phase 2/3/4/5 scale verbatim. **No new spacing values are introduced.**

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, chip internal padding |
| sm | 8px | Compact element spacing, field-error gaps |
| md | 16px | Default element spacing, card internal gaps |
| lg | 24px | Card padding, section padding |
| xl | 32px | Gap between major page sections |
| 2xl | 48px | Page top/bottom padding (`py-12`) |
| 3xl | 64px | Reserved — page-level spacing on wide viewports |

Exceptions (inherited, one new layout — not a token):
- **`12px`** permitted for tight intra-control gaps only: chip padding, segmented items, stepper gaps.
- **Touch targets** minimum **44×44px**; primary CTAs **48px** (`h-12`), secondary actions **44px**
  (`h-11`). The password show/hide toggle is exactly **44×44px**. Accessibility floor, not a spacing token.
- **Auth content width:** auth pages/cards use a narrowed column **`max-w-md` (28rem)** centered
  (`mx-auto`) — the focused-task counterpart to the admin `max-w-6xl` latitude. Mobile retains the
  `px-6` gutter. This is a **container-width choice, not a new spacing token**.
- **Field-error slots** reserve space (`min-h` on the error line container or fixed `gap`) so
  validation messages never shift the submit button — layout stability, not a token.

## Typography

Reuses the Phase 2/3/4/5 scale verbatim. **Exactly four sizes and exactly two weights across Phase 6.**

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 14px | 400 | 1.4 |
| Body | 16px | 400 | 1.5 |
| Heading | 20px | 600 | 1.25 |
| Display | 30px | 600 | 1.2 |

Declared weights: **400 (regular)** and **600 (semibold)** — exactly two.

**Focal point (visual anchor per screen):**
- `/login`: the **email submit CTA** («Войти» / «Создать аккаунт») is the anchor; the Telegram
  widget is secondary below the divider.
- `/reset`: the **email field + send CTA** is the anchor.
- `/reset/confirm`: the **save-password CTA** is the anchor.
- «Аккаунт»: the **login-methods list** is the anchor.

Rules:
- Map to Tailwind: `text-sm` (14), `text-base` (16), `text-xl` (20), `text-3xl` (30).
- Auth `h1`s are 30/600; card/section headings are 20/600; field labels, hints, widget notes,
  divider text are 14/400 secondary ink; body/intro copy is 16/400.
- Field errors are **14/400** in destructive red — never semibold, never 16px (errors must not
  out-shout the CTA).
- Email addresses and Telegram ids use `tabular-nums`; long values truncate 1 line with `title`.
- Body/secondary text stays on `text-zinc-600 dark:text-zinc-400`; headings on
  `text-black dark:text-zinc-50`.
