## Выручка и база MRR

### На каких подписках считаем MRR/ARR

| Option | Description | Selected |
|--------|-------------|----------|
| Активные ключи из KeyCache | Активный ключ → последний paid-заказ через `Order.keyId`; один ключ = одна строка | ✓ |
| Все paid-заказы за окно | Нормализовать каждый заказ; проще, но двойной счёт при продлении | |
| Заказы по статусу provisioned | Игнорирует истёкшие без продления | |

**User's choice:** Активные ключи из KeyCache
**Notes:** выбран рекомендованный вариант — источник истины о «живых» подписках.

### База денег для MRR

| Option | Description | Selected |
|--------|-------------|----------|
| Полученный кэш | `finalAmount - balanceUsed`, как в `lib/revenue.ts`; один источник истины | ✓ |
| Списочная ценность тарифа | Ближе к SaaS-стандарту, но расходится с revenue-панелью | |
| Оба (кэш + списочная) | Две карточки рядом | |

**User's choice:** Полученный кэш
**Notes:** консистентность с существующей revenue-панелью признана важнее «маркетингового» MRR.

### Бонусные дни (0 ₽ продления, компенсации)

| Option | Description | Selected |
|--------|-------------|----------|
| Исключить из MRR, отдельная метрика | Деньги не искажаются, видно размер goodwill | ✓ |
| Игнорировать полностью | Бонусные подписки невидимы в базе | |
| Включать по прайсу | Завышает выручку на неоплаченном | |

**User's choice:** Исключить из MRR, отдельная метрика

### Нормализация подписок разной длины

| Option | Description | Selected |
|--------|-------------|----------|
| Месячный эквивалент | `finalAmount / (срок_дней / 30)`; не зависит от окна | ✓ |
| Про-рата по календарю | Точнее для дневных графиков, зависит от окна | |

**User's choice:** Месячный эквивалент

### Знаменатели ARPU/ARPPU

| Option | Description | Selected |
|--------|-------------|----------|
| Все юзеры / платящие | ARPU = выручка / все зарегистрированные; ARPPU = выручка / платящие | ✓ |
| Активные за период | «Живая база», ближе к вовлечённости | |
| Только ARPPU | Честнее для VPN, но теряем базу | |

**User's choice:** Все юзеры / платящие
**Notes:** вопрос задан в блоке про структуру, относится к определениям метрик.

## providerCost: источник

### Откуда берём себестоимость ключа

| Option | Description | Selected |
|--------|-------------|----------|
| Сохранённый quote + доп. вызов при manual | При provisioning сохраняем provider-quote; при `source='manual'` — доп. `/pricing` только для cost | ✓ |
| Всегда свежий quote при выдаче | Себестоимость на момент выдачи, может отличаться от момента покупки | |
| Из дельты баланса | Фактическое списание, но баланс шумит от параллельных операций | |

**User's choice:** Сохранённый quote + доп. вызов при manual
**Notes:** учтено, что `resolveTariffQuote` (`lib/pricing.ts:94`) при ручном прайсе вообще не запрашивает provider-quote. Недоступность quote не блокирует выдачу (`providerCost = null` + лог).

### renew/upgrade

| Option | Description | Selected |
|--------|-------------|----------|
| Та же логика, per-order | `providerCost` на каждый заказ, включая renew/upgrade (upgrade — по дельте) | ✓ |
| Только первые покупки | Проще, но искажает unit-экономику продлений | |

**User's choice:** Та же логика, per-order

### Заказы до введения поля (cost = null)

| Option | Description | Selected |
|--------|-------------|----------|
| «—» + флаг покрытия | Маржа «—», период помечается «cost известен для N из M» | ✓ |
| Бэкфилл по текущему прайсу (estimated) | Приблизительно, отдельно от точных | |
| Только новые периоды | Старые периоды скрыты | |

**User's choice:** «—» + флаг покрытия
**Notes:** ретро-оценку решили не смешивать с фактом.

## Пересчёт, джоб, backfill

### Что кладём в daily_metrics

| Option | Description | Selected |
|--------|-------------|----------|
| Сырые агрегаты + производные на лету | В таблице агрегаты за день; MRR/ARPU/waterfall считаются в `lib/analytics`; «сегодня» — live | ✓ |
