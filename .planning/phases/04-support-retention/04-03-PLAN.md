In `lib/outbox.ts` add:
- `export const NOTIFY_TICKET_REPLY = "notify-ticket-reply";` and `export const REMIND_EXPIRY = "remind-expiry";`
- `export interface NotificationInput { type: string; dedupeKey: string; userId?: number; ticketId?: string; ticketMessageId?: string; keyId?: string }`
- `export async function enqueueNotification(input: NotificationInput): Promise<void>` → `prisma.notification.upsert({ where: { dedupeKey: input.dedupeKey }, update: {}, create: { ...input } })` — idempotent; a second enqueue is a no-op.
- `export interface ClaimedNotification { id: string; type: string; dedupeKey: string; userId: number | null; ticketId: string | null; ticketMessageId: string | null; keyId: string | null; attempts: number }`
- `export async function claimNextNotification(type: string): Promise<ClaimedNotification | null>` → candidate `findMany({ where: { status: "pending", type, nextAttemptAt: { lte: new Date() } }, orderBy: { createdAt: "asc" }, take: 10 })`, then per-row conditional `updateMany({ where: { id, status: "pending" }, data: { status: "processing" } })`; return on `count === 1`.
- `markNotificationDone(id)`, `rescheduleNotification(id, nextAttemptAt, reason)`, `markNotificationFailed(id, reason)` — all use `updateMany` (a vanished row is a no-op, mirroring lib/outbox.ts:83-121).

In `lib/worker.ts`: add `drainDeliveryNotifications(telegram)` that, for each of `[NOTIFY_TICKET_REPLY, REMIND_EXPIRY]`, claims up to `DRAIN_BATCH` and dispatches via `dispatchTicketNotification` (Task 2) / the reminder dispatcher (plan 04-08); on `retryable_error` → `rescheduleNotification(..., backoffMs(job.attempts + 1), "telegram")`, otherwise `markNotificationDone`. Call it from `drainOutbox` AFTER the order-notify loops only when `opts.telegram` is present, so a sender-less drain leaves rows `pending` (proven 03-07 pattern). For this plan, guard the reminder branch behind a lazy import so 04-08 can add it; a row whose dispatcher is not yet wired must remain `pending`, never be marked done.

Write `tests/unit/notifications-queue.test.ts` (DB-backed, `tests/unit/outbox-worker.test.ts` cleanup/truncation style): `enqueueNotification` twice with the same dedupeKey creates exactly one row; `claimNextNotification` is single-winner (two sequential claims of one row → one non-null); a second claim of the same row returns null; `rescheduleNotification` sets `pending` + increments attempts; sender-less `drainOutbox()` leaves a pending notification pending.
