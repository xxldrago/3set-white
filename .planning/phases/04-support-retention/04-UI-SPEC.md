# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Extends Phase 3's approved contract, which extends Phase 2's.** Phases 2–3 already locked the
spacing scale, the four type sizes / two weights, the 60/30/10 zinc + `#171717` accent + `#dc2626`
destructive palette, the semantic status-chip palette, the inline destructive-confirm pattern, the
skeleton/error copy catalog, and the RU i18n discipline. Phase 4 **introduces no new tokens, fonts,
icons, or component library** — it composes support/retention surfaces from the same primitives and
extends the status palette with three ticket states (`open`/`answered`/`closed`) that reuse existing
hex. This phase does introduce **new form primitives** (text input, textarea, image file picker),
which are specified here as a first-party extension of the same token set.

**Rendering-dependency notes (contract, not decoration):**
- **Attachments are served through a gated same-origin BFF route** (D-56): `/api/tickets/{ticketId}/attachments/{attachmentId}`.
  The route authorizes owner-or-admin and streams the stored file; there is **no public URL, no
  signed-CDN URL, no third-party image host**. Inline thumbnails are plain `<img src>` to that
  same-origin route (the session cookie rides along); they are never emitted as raw stored paths.
- **Support-reply visibility is outbox-driven** (D-57): the cabinet does not poll. It reflects the
  latest thread state on navigation / manual refresh; the bot pushes the reply to the owning `chatId`.
- **The expiry reminder is a Telegram-only surface** (D-60..D-63): a cron push with an inline button.
  It has no cabinet route; the cabinet-side equivalent is the existing Phase 2/3 key status + renew UI.

## Support Surfaces & Interaction Contract

### 1. Ticket list (`/support`, server component)

- Session-gated; redirect to `/login` on `SessionError` (same as `app/keys/[id]/page.tsx`).
- Header: `ticket.listTitle` («Обращения»). **Count header** when ≥ 2 rows via
  `tp('ticket.count', n)`. A primary CTA `ticket.cta` («Создать обращение») links to `/support/new`.
- **Row anatomy** (`article`, card surface, `p-6`):
  1. Subject — `text-xl font-semibold break-words`, single line clamped with `truncate` + full value
     via `title` (long-text backstop).
  2. `TicketStatusChip` — right-aligned; trail with the unread badge when `unread > 0`.
  3. Last activity — `ticket.lastActivity` («Обновлено {date}») at `text-sm` secondary ink,
     `DD.MM.YYYY · HH:mm` (ru-RU).
  4. Preview — last message text, `text-sm` secondary ink, `truncate` (1 line).
  - Ordering: newest activity first. Rows link to `/support/{id}`.
- **Unread badge** (D-58): accent-filled circle — `inline-flex h-6 min-w-6 items-center justify-center
  rounded-full bg-foreground px-2 text-sm font-semibold tabular-nums text-background`. Displays the
  count, capped at `99+`. **Hidden entirely when `unread === 0`** (never a zero badge). This is a
  deliberate accent reservation (see Color).
- Reuses the Phase 2/3 error mapping (`common.errorLoad` / `common.errorUnavailable` /
  `common.errorRateLimit`) and the `SkeletonRows` fallback.

### 2. Ticket thread (`/support/[id]`, server component + client islands)

- Session-gated; `notFound()` when the ticket is not owned by the caller (non-owned ≡ 404, matching
  the keys/orders ownership rule). Support-reply bodies are user-visible only to the owner.
- Heading: subject as page `h1` (30/600, `break-all`), followed by `TicketStatusChip` and a
  secondary «Обновить» control (`common.refresh`) that calls `router.refresh()`.
- **Thread body** — `flex flex-col gap-3`; messages oldest→newest:
  - **User message:** row `self-end max-w-[85%]`; bubble card surface with a subtle self tint
    `bg-black/[.03] dark:bg-white/[0.06]`.
  - **Support message:** row `self-start max-w-[85%]`; plain card surface; a sender label
    `support.senderLabel` («Поддержка») at `text-sm font-semibold` above the body.
  - **Bubble:** `rounded-2xl border border-black/10 p-4 dark:border-white/15`. Body 16/400/1.5 with
    `whitespace-pre-wrap break-words` (preserves newlines; long URLs never overflow).
  - **Timestamp:** `text-sm` secondary ink, `tabular-nums`, `DD.MM.YYYY · HH:mm`, placed under the
    bubble inside the same alignment column.
  - **Attachments** render inline inside their bubble (see §4). No lightbox this phase — tapping a
    thumbnail opens the gated file in a new tab.
- **Mark-read on open** (D-58): `MarkReadOnOpen` POSTs `/api/tickets/{id}/read` exactly once on
  mount (guarded by a ref), then `router.refresh()`; the list/nav unread badge clears. Never on
  server render. A failed mark-read is silent (no error surface) — it retries on next open.
- **No polling.** Support replies arrive via the existing outbox → bot push + next cabinet load. A
  reply is reflected on `common.refresh` / navigation.
- **Closed ticket** (D-50/D-59): the composer stays present with `ticket.reopenNote`
  («Ответ откроет обращение заново.»). Sending a message reopens the thread in place (status
  `reopens` → `open`); it never creates a new ticket.
- Loading: skeleton bubbles (`h-20 animate-pulse rounded-2xl`), 3 rows. Error: `common.errorLoad` +
  `common.retry`. A thread with no messages is treated as `partial` — render the subject plus the
  composer, never an empty void.

### 3. Ticket creation (`/support/new`, client island)

- Fields (all labels `text-sm` secondary ink, all controls focus-ringed on the accent):
  1. **`ticket.subjectLabel`** («Тема») — single-line `<input>`; `ticket.subjectPlaceholder`
     («Кратко опишите вопрос»); `maxLength=120`; required.
  2. **`ticket.messageLabel`** («Сообщение») — `<textarea>`; `ticket.messagePlaceholder`
     («Опишите проблему подробнее…»); `maxLength=4000`; required.
  3. **Attachment** — optional single image, `ticket.attachCta` («Прикрепить изображение»).
- **Form primitives (new; token-conformant):**
  - Input: `h-12 w-full rounded-2xl border border-black/[.08] bg-white px-4 text-base text-black
    placeholder:text-zinc-500 dark:border-white/[.145] dark:bg-zinc-900 dark:text-zinc-50
    dark:placeholder:text-zinc-500`; focus ring via the global `outline-2 outline-offset-2`.
  - Textarea: same shell with `min-h-28 py-3` (112px, multiple of 4) and `resize-y`.
  - File picker: native `<input type="file" accept="image/jpeg,image/png,image/webp">` visually
    hidden, driven by a secondary-button `<label>` (`h-11 rounded-full border …`). Chosen file shows
    `ticket.attachSelected` («Выбрано: {name}») truncated 1 line + a secondary `ticket.attachRemove`
    («Убрать»).
- **Client-side validation (before any request):** reject files > 5 MiB with `ticket.attachTooLarge`;
  reject non-jpg/png/webp with `ticket.attachBadType`; show both in a `role="alert"` block and keep
  the rest of the form intact. Server re-validates (5 MiB + type + `sharp` downscale) — the UI
  message is never the security boundary.
- Submit CTA `ticket.submit` («Отправить»): disabled while subject or message is blank (trimmed), and
  while an attachment is uploading or the request is in flight. In-flight → label `ticket.submitLoading`
  («Отправляем…») + `disabled`. Success → redirect to the created thread. Failure → `ticket.sendError`
  + `common.retry`; the typed text and selected file are retained.
- While an attachment uploads, the send CTA is locked and the picker shows a small
  `h-40 w-full animate-pulse rounded-xl bg-black/5` preview placeholder — no progress bar (single
  small file).

### 4. Attachments (D-53..D-56, SUP-02)

- **Image-only** jpg/png/webp, ≤ 5 MiB, downscaled server-side via `sharp`. Rendered inline in the
  thread as `AttachmentImage`:
  - Thumbnail `rounded-xl border border-black/10` with a reserved aspect box (`max-h-64 w-auto`) and
    explicit `width`/`height` so the thread never reflows on load.
  - `<img loading="lazy" decoding="async">` against the gated BFF route; `alt` = `ticket.attachmentAlt`
    («Вложение»). Never a stored path, never a public URL.
  - **Loading:** a skeleton tile `h-40 w-full animate-pulse rounded-xl bg-black/5` until `onload`.
  - **Error:** an `AttachmentImage` error tile — secondary-ink `ticket.attachmentError`
    («Не удалось загрузить вложение») inside a bordered box, never a broken-image icon.
- Both channels (cabinet multipart, bot `getFile`) converge on one attachment contract (D-55); the
  user-visible result is identical.

### 5. Expiry reminder (PAY-05 / D-60..D-63, Telegram-only)

- Daily cron push, sent per key with `expiresAt ≤ now + 3 days` (includes trial keys, D-63). No
  cabinet route and no email; the cabinet already exposes the key status via Phase 2.
- **Non-trial:** `bot.expiryReminder` («Подписка истекает {date}. Продлите, чтобы не потерять
  доступ.») + one inline button `renew.cta` («Продлить») → the Phase 3 renew flow (`key:renew:*`).
- **Trial:** `bot.expiryReminderTrial` («Trial-период заканчивается {date}. Оформите полную
  подписку, чтобы продолжить.») + one inline button `key.buyCta` («Купить подписку») → the tariff
  section. **Never** a renew button on a trial key (D-44/PAY-03 already forbid it).
- `{date}` is `DD.MM.YYYY`; the message never contains a raw key id, provider status, or error text.
- Reminder copy is deliberately soft and useful, never alarmist (Specific Ideas); it is not a
  destructive or money-moving action — it only deep-links into the existing renew/buy pipeline.

### 6. Bot support channel (SUP-01/SUP-03 parity)

- Persistent menu gains `bot.menuSupport` («Поддержка»). Selecting it replies `bot.supportPrompt`
  («Напишите ваш вопрос одним сообщением. Можно приложить фото или скриншот.»).
- The next text message (optionally with a photo) creates a ticket via the same service the cabinet
  BFF uses; success → `bot.ticketCreated` («Обращение создано. Мы ответим здесь и в кабинете.»),
  failure → `bot.ticketError`. The bot never echoes provider/API errors (D-19/D-24).
- **Fan-out (SUP-03):** a support reply is delivered by the outbox worker to the owning `chatId`
  (`bot.ticketReply` = «Ответ поддержки:» + body) and is simultaneously visible in the cabinet
  thread + increments the cabinet unread badge (D-57/D-58).
- Bot strings are sliced under Telegram's 4096-char limit (Phase 2 slicing pattern).

### 7. Cabinet entry / nav (unread parity)

- The home page nav and thread list expose `/support` via `ticket.toSupport` («Поддержка»), rendered
  by `SupportEntry` with the unread badge when `unread > 0` (hidden at 0). Entry is available to any
  signed-in user; tickets are per-owner.

Reuses the Phase 2/3 scale verbatim. **No new spacing values are introduced.**

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, badge internal padding |
| sm | 8px | Compact element spacing, list-row internal gaps |
| md | 16px | Default element spacing, bubble/card internal gaps |
| lg | 24px | Card padding, section padding |
| xl | 32px | Gap between major page sections |

| 3xl | 64px | Reserved — not expected in the mobile support layout |

Exceptions (inherited, still binding):
- **`12px`** permitted for tight intra-control gaps only: chip padding, stepper/segmented items.

- New form primitives use `h-12` (input), `min-h-28` (textarea), `h-11` (file-picker label); do not
  introduce `h-10` into Phase 4 controls.
- Thread bubbles cap at `max-w-[85%]`; thumbnails cap at `max-h-64`.

## Typography

Reuses the Phase 2/3 scale verbatim. **Exactly four sizes and exactly two weights across Phase 4.**

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 14px | 400 | 1.4 |
| Body | 16px | 400 | 1.5 |
| Heading | 20px | 600 | 1.25 |
| Display | 30px | 600 | 1.2 |

Declared weights: **400 (regular)** and **600 (semibold)** — exactly two.

**Focal point (visual anchor per screen):**
- `/support` (ticket list): the row's subject + `TicketStatusChip` is the scanning anchor; the unread badge is the attention cue.
- `/support/[id]` (thread): the newest unread support bubble is the anchor; the composer is the persistent footer.
- `/support/new` (composer): the submit CTA («Отправить сообщение») is the anchor after a valid message is entered.

Rules:
- Map to Tailwind: `text-sm` (14), `text-base` (16), `text-xl` (20), `text-3xl` (30).
- Message bodies are 16/400/1.5 (`whitespace-pre-wrap`); timestamps/metadata are 14/400; the ticket
  subject in a list is 20/600, and the thread heading is 30/600.
- Status chips and the sender label («Поддержка») are 14/600. No new emphasis weight (never 500).
- Unread counts and timestamps/dates use `tabular-nums`.
- Body/secondary text stays on `text-zinc-600 dark:text-zinc-400`; headings on
  `text-black dark:text-zinc-50`.

## UI Considerations

> Shape-rooted UI *state* coverage (empty / loading / error / populated / partial / overflow /
> zero-one-many / long-text). Empty- and error-state COPY lives in `## Copywriting Contract` above;
> this section covers state coverage and REFERENCES those rows rather than restating copy.

Applicable state considerations resolved: **20 covered, 3 backstop, 0 unresolved**.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | ticket-list | ✅ covered | Zero tickets renders `ticket.emptyHeading` + `ticket.emptyBody` + `ticket.cta`; verified by an empty-state render test. |
