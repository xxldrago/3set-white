# Phase 06 Plan 09: Bot-redirect login device-code binding (CR-01) Summary

**Bot-delivered sha256-only confirmation code now binds the authorizing Telegram user to the issuing browser, so a bot-redirect login-CSRF hijack mints no session while the legitimate flow keeps working with one extra code entry.**

## Accomplishments
- `TelegramLoginToken` gains `codeHash` (sha256) and `codeAttempts`; migration `20261005212213_telegram_login_code` applied and client regenerated to `generated/prisma`.
- `bindLoginToken` issues a 6-digit code, persists only its hash, and resets `codeAttempts` in the same atomic bind as `telegramId`; it returns the plaintext code to the bot only.
- `consumeLoginToken` requires the code (length-guarded timing-safe compare), returns `bad_code` on mismatch, increments attempts atomically, and invalidates the token at the 5-attempt cap.
- Bot `/start login_<token>` DMs `bot.loginCode` with the code; `consume` requires a 6-digit code and maps `bad_code` to the same generic 401 as a wrong claim.
- `TelegramBotLoginButton` stops auto-consuming on `ready` and renders a numeric code-entry state (wrong code clears+retries, 409 falls back to `expired`), with reserved `min-h` so the swap does not shift layout.
- CR-01 covered by a failing hijack vector, a passing correct-code vector, and an attempt-cap invalidation vector; full suite green (427 tests).

## Decisions Made
- Hash-only persistence: neither `status` nor `consume` returns the code; the bot DM is the sole delivery channel (T-06-09-03).
- Wrong code → generic 401 identical to a wrong claim (no oracle); the attempt cap self-invalidates the token (T-06-09-02).
- Kept the anonymous bot login usable: the only added step is typing the code the user sees in their own Telegram chat (D-94 preserved — the bot stays TG-only).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] consume route would mint a session from the new `bad_code` result**
- **Found during:** Task 1 (Schema + login-token service code binding)
- **Issue:** Adding `{ kind: "bad_code" }` to `ConsumeLoginTokenResult` left the route's `if/else` chain without a matching branch, so `tsc` failed and, at runtime, execution would fall through to `signSession(result.userId, ...)` with `undefined` values — a real session-minting bug.
- **Fix:** Added an explicit `bad_code` branch returning the generic 401 (same as a wrong claim), before the session-mint line. Task 2 then wired the code schema/pass-through.
- **Files modified:** `app/api/auth/telegram-bot/consume/route.ts`
- **Verification:** `npx tsc --noEmit` clean; Task 3's hijack vector confirms no session cookie on a wrong code.
- **Committed in:** `974fde9` (Task 1 commit)

**2. [Rule 3 - Blocking] `consumeLoginToken` `code` made optional for call-site compatibility**
- **Found during:** Task 1
- **Issue:** The plan specified a required `code` parameter, but `tsconfig` type-checks the (not-yet-updated) route, so a required parameter would fail Task 1's `tsc --noEmit`.
- **Fix:** Typed `code?: string | undefined | null`; runtime treats a missing/non-string code as `bad_code`. Task 2 passes the code explicitly, so security is unchanged.
- **Files modified:** `lib/telegram-login.ts`
- **Verification:** Task 1 `tsc` clean; Task 3 wrong/missing-code vectors fail closed.
- **Committed in:** `974fde9` (Task 1 commit)

## Issues Encountered
- A hijack attempt that omits the code entirely is rejected by the zod schema with 400 (not 401), while a well-formed wrong code returns the specified 401. The security acceptance ("hijack returns 401 / mints no session") is met via the wrong-code path; the no-code path is asserted as a non-200 with the token left intact.
