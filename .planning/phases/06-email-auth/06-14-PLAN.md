<objective>
Close the new Critical from 06-VERIFICATION.md truth 13 / 06-REVIEW.md CR-01: the unauthenticated password-reset request route calls the login rate-limit helper with the raw email, so five anonymous reset requests drive the shared `(email, EMAIL_ONLY_IP)` account-wide row to the lock threshold. The victim's next `POST /api/auth/email/login` 429s before the password is checked, and the same shared gate also blocks reset — a remote account-lockout DoS with no self-service recovery.

**As a** VPN customer with an email account (AUTH-02/AUTH-04), **I want to** have my login and password-reset remain reachable while an anonymous party spams reset requests, **so that** a known email address cannot be used to lock me out.

Fix: give the reset-mail throttle its own namespaced counter (`__reset__:<normalizedEmail>`) so it never writes the login sentinel row, and harden `bumpAttempt` so the lock cannot be evaded by a parallel burst of guesses. Login and reset-mail throttles must NOT share lock state; the CR-02 account-wide counter for the LOGIN route stays exactly as-is.

Purpose: make the CR-02 fix safe — it must protect login without becoming a denial-of-service lever.
Output: isolated reset throttle wrappers, a route wired to them, an atomic counter, and regression tests proving both directions.

Note on decision fidelity: this preserves D-84 (exponential backoff + temporary lock, no captcha), D-88 (1h one-time reset token) and the D-89 accepted reset-request existence oracle; no decision is revisited or reduced.
</objective>
